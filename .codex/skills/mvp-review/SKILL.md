# MVP Review

작은 제품이 약속한 핵심 경험을 실제로 완성했는지 검토한다. 일반적인 스타일 교정이나 대규모 리팩터링은 이 스킬의 목적이 아니다.

## 시작 전

1. MVP 기획서, 이슈, README 등 완료 조건의 근거를 확인한다. 저장소에 `MVP_SPEC.md`가 있으면 우선 사용한다.
2. `git status`, staged diff, unstaged diff로 검토 범위를 확정한다.
3. 실제 실행 또는 테스트 결과가 있으면 함께 확인한다. 실행하지 못했다면 그 사실을 검토 결과에 남긴다.

## 검토 기준

### 범위와 사용자 흐름

- 구현이 명시된 완료 조건을 충족하는가?
- 핵심 흐름이 시작부터 성공 또는 실패 피드백까지 끊기지 않는가?
- 기획에 없는 기능이 복잡도나 유지보수 비용만 늘리지 않는가?

### 상태와 실패 처리

- 사용자 동작의 성공·실패에서 상태가 일관되게 갱신되는가?
- 잘못된 입력, 빈 데이터, 한계 상태, 중복 실행이 안전하게 처리되는가?
- 저장 또는 복원이 있다면 변경 시점과 복원 후 상태가 서로 일치하는가?

### 책임 분리

- 표시 계층에 제품 규칙이나 영속화가 섞이지 않는가?
- 핵심 규칙이 UI 또는 프레임워크에 불필요하게 묶이지 않는가?
- 현재 범위에 비해 과도한 추상화나 미사용 구조가 없는가?

### 검증 가능성

- 완료 조건을 재현할 수 있는 실행 절차 또는 테스트가 있는가?
- 주요 성공 경로뿐 아니라 실패 경로도 확인됐는가?
- 발견한 위험이 코드, 문서, 실행 결과 중 무엇에 근거하는지 명확한가?

## 결과 형식

발견 사항만 심각도 순으로 보고한다. 각 항목에는 파일·줄 또는 재현 절차, 사용자 영향, 최소 수정 방향을 포함한다.

```text
## MVP Review

### Critical
- 없음

### Warning
- [파일:줄 또는 재현 절차] 문제와 사용자 영향
  - 최소 수정 방향: ...

### Info
- ...

## 확인한 범위
- 기획 근거: ...
- 코드/문서: ...
- 실행 또는 테스트: ...
```

문제가 없으면 `Critical: 없음`, `Warning: 없음`을 명시하고, 확인하지 못한 영역을 숨기지 않는다. 리뷰는 보고 작업이며, 사용자의 별도 요청 없이 코드를 수정하거나 커밋하지 않는다.
